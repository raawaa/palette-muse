#1 CapturedColor 的 hex String → Rgb 值类型

涉及的模块

core/CapturedColor.kt:28 core/ColorAnalyzer.kt:59 core/ColorMatcher.kt:18-19 data/model/PhotoEntity.kt data/model/ThemeEntity.kt data/repository/ThemeMatcher.kt

推荐强度

Strong

问题

CapturedColor.hex 是一个 String，但整个流水线实际上操作的是数值 RGB。 ColorAnalyzer.extractCapturedColor 从 k-means 得到 Int 质心， 然后转换为 String 十六进制（第 59 行）。每个消费者——ColorMatcher、 ThemeMatcher——都会重新解析这个 String 为 Int 或 Rgb 才能使用。

数据路径实际是：Int → String → Int → Rgb → Lab， 包含三个多余的转换步骤。这是一个数据表示泄露——表示层格式（人可读的十六进制） 侵入了核心流水线，强迫每次使用都进行解析。

解决方案

将 CapturedColor.hex 替换为 CapturedColor.rgb: Int（原始 ARGB）， 并提供一个 val hex: String 计算属性供 UI 层使用。消费者现在直接使用 rgb 而无需解析。

ThemeEntity.representativeHex 和 PhotoEntity.capturedHex 同理迁移为 representativeRgb: Int / capturedRgb: Int， 在序列化到 Room 时保持数值形式。

收益

  • 局部性：颜色表示现在集中在一个地方（Int），所有消费者使用相同的数据类型。解析逻辑不再分散在 ColorMatcher、ThemeMatcher 和 UI 工具函数之间。
  • 杠杆效应：一个数据库迁移（hex String → rgb Int）使整个流水线从 5 步减少到 3 步。每个下游消费者自动获益。
  • 可测性：移除所有解析步骤，消除了一整类因十六进制格式差异（前缀 # vs 无前缀、大小写）导致的错误。测试可以直接使用数值断言。
  • 流水线中的 CPU 周期减少约 3 次字符串分配 + 3 次解析 每次捕获。

⚠️ ADR 检查

ADR-0006 建立了 Rgb 数据类并解耦了 ColorMatcher 的 Android 依赖。 本提案在此基础上更进一步——将 hex String 提升为 rgb Int——并不与任何现有决策冲突。 ADR-0003 锁定了 ThemeMatcher 的形状（类 + 私有阈值）， 但并未对其消费的数据类型做出裁决；传递 Int 而非 String 不会改变其形状。 数据库迁移（String → Int 列）需要相应的 Room 迁移；这是可接受的成本。

Strong

#2 ColorAnalyzer 编排逻辑可单元测试化

涉及的模块

core/ColorAnalyzer.kt:33-70 core/KMeansColorQuantizer.kt core/PerceptualColorFamilies.kt core/CaptureConfidencePolicy.kt

推荐强度

Strong

问题

ColorAnalyzer.extractCapturedColor(bitmap: Bitmap) 是整个颜色流水线的顶端——它编排了下采样、k-means 聚类、感知色族合并、置信度信号计算和 CapturedColor 组装。 然而，因为它的签名接受 Android Bitmap，整个编排只能通过插桩测试来覆盖。

删除测试：删除此方法意味着下采样 + k-means + 合并 + 信号计算——所有这些都重新分散到它们的调用者（CaptureViewModel）中。 复杂性确实是集中的。但该模块因为缺少内部接缝而显得浅薄——使纯逻辑依赖于 Android Bitmap。

目前，仅辅助函数 computeTopVsSecondRatio 有单元测试（ColorAnalyzerRatioTest， 6 个分支）。主方法 extractCapturedColor 的编排逻辑——参数顺序、默认常量、分支逻辑——完全没有 通过 JVM 测试来验证。

解决方案

将纯粹的算法步骤从 Android 边界中提取出来：

  • downscaleBitmap(bitmap: Bitmap, maxPx: Int): IntArray — 缩小尺寸并提取像素（仍是 Android 依赖，但提取到一个单一职责函数）
  • analyzePixels(pixels: IntArray): CapturedColor — 纯 Kotlin 编排：k-means → 感知合并 → 置信度信号 → CapturedColor

extractCapturedColor 变为： fun extractCapturedColor(bitmap: Bitmap) = analyzePixels(downscaleBitmap(bitmap, MAX_PIXELS))

现在 analyzePixels 是纯 Kotlin，可直接用于 JVM 单元测试。

收益

  • 可测性：analyzePixels 接受 IntArray——在 JVM 上可直接构造。回归测试可以覆盖边缘情况（纯色、噪点图像、渐变、小尺寸），无需模拟器。
  • 局部性：编排逻辑（k-means 参数、默认值、分支顺序）现在集中在一个纯 Kotlin 函数中，而不是跨 Android 边界分布。
  • 杠杆效应：对一个纯函数的测试覆盖了整个颜色流水线的调用树。对 analyzePixels 的一次更改会安全地影响所有调用者。
  • 速度：这些测试可以在亚毫秒级运行，而不是需要模拟器启动的插桩测试。

⚠️ ADR 检查

ADR-0002 建立的模式——提取纯 Kotlin 顶层函数——这里再次应用。 ADR-0006 为 ColorMatcher 做了类似的事情（从 Android 框架解耦纯逻辑）。 本提案遵循相同的经实战检验的模式。无冲突。

Strong

#3 BitmapStorage 接口提取

涉及的模块

data/repository/BitmapStorage.kt di/AppModule.kt ui/capture/CaptureViewModel.kt ui/export/ExportViewModel.kt

推荐强度

Strong

问题

BitmapStorage 是一个 @Singleton @Inject 具体类， 将文件 I/O（保存、删除、写入到 MediaStore）直接绑定到其接口。 CaptureViewModel 依赖它来保存和删除捕获文件； ExportViewModel 依赖它来保存到系统相册。

目前 CaptureViewModel 接受 6 个具体依赖项（第 61-67 行）。 BitmapStorage 是唯一一个包含 I/O 副作用的依赖项——其他依赖项（ThemeRepository、 ColorAnalyzer、ThemeMatcher）是纯函数或可模拟的。 将 BitmapStorage 提升为接口会打开一条接缝，使 ViewModel 可以在 JVM 上进行纯单元测试。

删除测试：删除 BitmapStorage 会将其文件 I/O 分散到 CaptureViewModel 和 ExportViewModel 中，并且 将文件路径约定（captures/capture_{ts}.jpg）复制到两个地方——这是真正的复杂性。 模块不浅薄；它缺少的是一个合适的接缝。

解决方案

从具体类中提取 interface BitmapStorage：

  • interface BitmapStorage { fun saveCapture(…); fun deleteCapture(…); fun saveToGallery(…) }
  • 当前实现重命名为 FileBitmapStorage 并实现该接口。
  • 添加一个 InMemoryBitmapStorage 用于测试（在内存映射中保留字节）。
  • CaptureViewModel 和 ExportViewModel 依赖接口。
  • 在 Hilt 模块中绑定：@Binds BitmapStorage FileBitmapStorage。

收益

  • 可测性：CaptureViewModel 和 ExportViewModel 现在可以在纯 JVM 测试中构造，使用内存中的 fake 存储，无需文件系统副作用。
  • 局部性：文件路径约定编码在 FileBitmapStorage 中，而不是在 ViewModel 中或在路径上硬编码。
  • 杠杆效应：一个接缝（接口）允许两种适配器——生产环境的文件和测试环境的内存。同时为未来提供可能性（例如，加密存储适配器、云同步适配器）。
  • 遵循 codebase-design 原则："两个适配器意味着一个真实的接缝。" 在这里，我们已经有删除（deleteCapture）和保存（saveCapture）两个适配器，它们通过具体类绑定在一起。接口提取使接缝变得明确。

⚠️ ADR 检查

无冲突。ADR-0018 规定捕获写入 filesDir/captures/ 且不使用 MediaStore——这由 FileBitmapStorage 强制执行，不受接口提取影响。 ADR-0018 还规定了 deleteCapture 的语义 （尽力而为，忽略 I/O 错误）——这些语义保留在适配器中。

Worth exploring

#4 PosterRenderer 布局数学与 Canvas 绘制分离

涉及的模块

core/PosterRenderer.kt:27-147 ui/export/ExportViewModel.kt

推荐强度

Worth exploring

问题

PosterRenderer.render 将布局数学（计算网格位置、胶片条矩形、日记布局偏移量） 与 Canvas 绘制命令（drawBitmap、drawText、drawRoundRect） 混合在一个大函数中。四个模板渲染器（renderGrid、renderFilm、 renderJournal、renderMinimal）各有自己的布局逻辑，嵌入在 Canvas 调用中。

删除测试：删除 PosterRenderer 会将 120 行布局 + Canvas 逻辑 分散到 ExportViewModel 中。复杂性是真实的，但布局数学和 Canvas 绘制之间没有接缝—— 它们无法独立测试。

PosterRendererTest（插桩测试）渲染真实位图并检查输出尺寸，但无法测试布局细节 （照片是否在正确的位置、文本是否居中）而不进行复杂的位图比较。

解决方案

提取布局数学到纯函数中，返回描述性的数据结构，然后由 Canvas 渲染器消费：

  • PosterLayoutEngine.computeGridLayout(photoCount, w, h): List<Rect>
  • PosterLayoutEngine.computeFilmLayout(photoCount, w, h): FilmLayout
  • 每个函数返回位置/尺寸/间距，而不触及 Canvas。

然后 PosterRenderer 保持不变，但现在调用 PosterLayoutEngine 来获取布局，再进行绘制。布局逻辑现在可以在 JVM 上通过纯函数进行单元测试。

收益

  • 可测性：布局逻辑（网格间距、胶片偏移量、日记行高、填充）可以在 JVM 上进行单元测试，无需位图渲染。测试可以断言确切的 RectF 坐标。
  • 局部性：布局算法集中在 PosterLayoutEngine 中，而不是分布在四个渲染器函数之间。
  • 杠杆效应：添加新模板时，只需要新的引擎函数和新的渲染器。测试新模板的布局不需要渲染位图。

⚠️ ADR 检查

ADR-0012 将 poster 预览统一到 Canvas 渲染器——但那是关于预览与导出渲染路径的合并， 而不是关于从绘制中分离布局数学。提取布局纯函数保持了渲染路径的完整性；它只是使逻辑可测试。 无冲突。

🏆 首选推荐

#1

CapturedColor hex String → Rgb 值类型

首选从 CapturedColor 类型泄露入手。原因如下：

  • 影响面最广——它触及流水线的每一层：ColorAnalyzer、ColorMatcher、ThemeMatcher、实体模型、Room DB。修复它会使整个流水线从 5 步减少到 3 步。
  • 消除一整类错误——十六进制格式差异（# 前缀、大小写、前导零）不能再悄悄进入系统。
  • 下游收益——一旦 CapturedColor 存储原始 Int，候选 #2（编排测试性）也变得更容易，因为 analyzePixels 返回的 Int 无需字符串转换即可传递。
  • 低成本、高确定性——类型变化是机械性的。Room 迁移需要额外的关注，但变更范围是明确且有限的。
  • 与现有 ADR 一致——建立在 ADR-0006 的 Rgb 类型基础上，不冲突。

候选 #3（BitmapStorage 接口）作为第二优先级，因为它解锁了 ViewModel 的 JVM 可测试性。 候选 #2（ColorAnalyzer 提取）在 #1 之后更易于实现，因为数据表示已经理顺。
